# @Replit Prompt Addendum — Recurrence, Tags, Descriptions, and Cosmic Overlay

You are continuing work on **Kieran’s LifeTrkr** in the `OKHP3/kierans-lifetrkr` repository.

This is an alignment pass for the existing client-only V1 app. Do not rewrite the project from scratch. Inspect the current routes and components first, especially:

* `/rituals`
* `/habits`
* `/calendar`

The current issue is that Rituals, Habits, and Calendar items behave too much like one-time appointments. Rituals and habits are semantically recurring by default, and calendar events also need recurrence support.

Implement a shared recurrence and metadata model that can be reused across all three areas.

---

# 1. Product direction

Keep the current V1 architecture:

* client-only;
* local/browser persistence;
* no backend for this pass;
* no Notion runtime database;
* no secrets in frontend code;
* no required external API dependency for this pass.

Notion remains the project hub/artifact ledger, not the app database.

# 2. Core problem to solve

Currently, adding a Ritual, Habit, or Calendar item appears to support only basic fields such as:

* title/name;
* date;
* start time;
* end time;
* location in Calendar.

That is insufficient.

Add support for:

1. recurrence;
2. frequency;
3. recurrence end conditions;
4. description;
5. category;
6. emoji-style tags;
7. filtering/sorting by category, tag, recurrence, and date;
8. optional cosmic/lunar/daily-wisdom overlay.

---

# 3. Domain clarification

Use these domain meanings:

## Ritual

A ritual is a recurring routine, usually made of one or more steps.

Examples:

* morning ritual;
* evening wind-down;
* medication routine;
* Sunday reset;
* card reading ritual;
* moon ritual;
* homework/study ritual.

A ritual should support recurrence and completion tracking by date.

## Habit

A habit is a recurring behavior tracked over time.

Examples:

* drink water;
* take medication;
* meditate;
* read;
* sleep routine;
* clean room;
* journal;
* stretch.

A habit should support recurrence, completion history, and simple progress.

## Calendar Event

A calendar event is a scheduled item that may be one-time or recurring.

Examples:

* appointment;
* class;
* work shift;
* family event;
* recurring reminder;
* medication window;
* moon phase event;
* daily card prompt.

Calendar items should support recurrence when user-created.

## Cosmic Overlay

Cosmic/lunar/astrological items should be read-only contextual events. They should not be mixed directly with user-created calendar events in the data model.

Examples:

* full moon;
* new moon;
* moon phase;
* seasonal marker;
* daily card;
* daily word of wisdom.

# 4. Shared recurrence model

Create or align toward a shared recurrence type.

Use TypeScript-style structure if the project is TypeScript. If the project is JavaScript, use the same shape in plain JS.

```ts
type RecurrenceFrequency =
  | "none"
  | "daily"
  | "weekly"
  | "monthly"
  | "yearly"
  | "custom";

type DayOfWeek =
  | "monday"
  | "tuesday"
  | "wednesday"
  | "thursday"
  | "friday"
  | "saturday"
  | "sunday";

type RecurrenceEnd =
  | { mode: "never" }
  | { mode: "onDate"; date: string }
  | { mode: "afterCount"; count: number };

type RecurrenceRule = {
  frequency: RecurrenceFrequency;
  interval: number;
  daysOfWeek?: DayOfWeek[];
  dayOfMonth?: number | null;
  startDate: string;
  end: RecurrenceEnd;
  exceptions?: string[];
};
```

Default recurrence:

```ts
{
  frequency: "none",
  interval: 1,
  startDate: today,
  end: { mode: "never" },
  exceptions: []
}
```

Do not overbuild advanced recurrence yet. V1 should support:

* does not repeat;
* daily;
* weekly;
* monthly;
* custom weekly days;
* ends never;
* ends on date;
* ends after N occurrences.

# 8. Data model alignment

Align existing entities toward these shapes without destructive migration.

## Ritual

```ts
type Ritual = {
  id: string;
  title: string;
  description?: string;
  steps?: RitualStep[];
  startTime?: string | null;
  endTime?: string | null;
  recurrence: RecurrenceRule;
  categoryId?: string;
  tags: string[];
  active: boolean;
  createdAt: string;
  updatedAt: string;
};
```

## Habit

```ts
type Habit = {
  id: string;
  title: string;
  description?: string;
  recurrence: RecurrenceRule;
  categoryId?: string;
  tags: string[];
  completedDates: string[];
  active: boolean;
  createdAt: string;
  updatedAt: string;
};
```

## Calendar Event

```ts
type CalendarEvent = {
  id: string;
  title: string;
  description?: string;
  startDate: string;
  startTime?: string | null;
  endTime?: string | null;
  location?: string;
  recurrence: RecurrenceRule;
  categoryId?: string;
  tags: string[];
  source: "user" | "mock" | "google" | "cosmic";
  createdAt: string;
  updatedAt: string;
};
```

## Cosmic Event

```ts
type CosmicEvent = {
  id: string;
  title: string;
  description?: string;
  date: string;
  type: "moon_phase" | "seasonal" | "daily_card" | "daily_wisdom";
  emoji?: string;
  source: "local" | "external";
};
```

Existing records should migrate safely:

* missing recurrence becomes `frequency: "none"`;
* missing description becomes empty;
* missing category becomes undefined or `uncategorized`;
* missing tags becomes `[]`.

Do not wipe existing user data in localStorage.

# 10. Cosmic/lunar/daily-wisdom layer

Add a lightweight V1 cosmic overlay, but do not make the app dependent on external services.

Preferred V1 implementation:

1. local deterministic moon phase calculation if simple;
2. local seeded daily card/wisdom generator;
3. optional placeholder adapter for future external APIs.

Do not add required API keys.

Do not add secrets.

Do not block the app if cosmic data fails.

The cosmic layer should provide:

```ts
getMoonPhaseForDate(date: string): CosmicEvent | null
getDailyCard(date: string): CosmicEvent
getDailyWisdom(date: string): CosmicEvent
getCosmicEventsForDateRange(startDate: string, endDate: string): CosmicEvent[]
```

Daily card/wisdom should be deterministic per date. It should not change every time the user refreshes the page.

Use a date-seeded selection from a local list.

Example tone:

```text
Card of the Day: The Lantern
A small step still counts as movement. Pick one thing that makes the room feel lighter.
```

Keep this framed as reflection, encouragement, or mood-setting. Do not present it as factual fortune-telling.
